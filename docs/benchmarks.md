# Benchmarks

Speed, output size and binary size of susut against the tools it is usually compared with.
Everything here is reproducible with [`scripts/bench/run.sh`](../scripts/bench/run.sh).

## Setup

- **Machine:** Apple M3, 8 cores, macOS 27.0.1, an otherwise idle laptop.
- **Versions:** susut 0.1.0 (release build), caesiumclt 1.5.0 (Homebrew), rimage 0.14.0
  (built from source with `--features build-binary`), jpegoptim 1.5.6.
- **Images:** synthetic, generated by [`gen_images.py`](../scripts/bench/gen_images.py).
  They are **not** real photographs, so absolute sizes will differ on your own files.
  - `imgs/`: 12 JPEGs, 3000x2000, 15.8 MB (half of them noisy).
  - `small_jpg/`, `small_png/`: the same images at 1500x1000 (JPEG 2.6 MB, PNG 17.4 MB).
  - `ui_png/`: 12 flat UI-like PNGs (rectangles and text), 1500x1000, 0.77 MB.
- **Timing:** [hyperfine](https://github.com/sharkdp/hyperfine), warm cache, output deleted
  before every run. Each tool at its default threading, or 8 threads (`rimage -t 8`);
  jpegoptim has no threading and is run through `xargs -P 8` where batches are involved.
- **Quality:** `-q 80` everywhere, AVIF speed 6, PNG at oxipng level 2.

## Speed

Mean ± standard deviation, lower is better. Run of 2026-10-31.

| Task | susut | caesiumclt | rimage |
|---|---|---|---|
| JPEG to JPEG, 12 images (20 runs) | **782 ± 67 ms** | 893 ± 57 ms | 863 ± 14 ms |
| JPEG, one image (15 runs) | 156 ± 5 ms | 148 ± 6 ms | 150 ± 3 ms |
| JPEG with 150 KB target, one image (8 runs) | **1.12 ± 0.00 s** | 1.19 ± 0.04 s | no such option |
| JPEG to WebP, 12 images (10 runs) | **942 ± 36 ms** | 1249 ± 42 ms | 1033 ± 49 ms |
| JPEG to AVIF, 12 images 1500x1000 (3 runs) | 2.04 ± 0.01 s | no AVIF | 2.04 ± 0.03 s |
| PNG lossless, 12 noisy images (5 runs) | 3.00 ± 0.50 s | 3.27 ± 0.44 s | 2.92 ± 0.16 s |
| PNG lossless, 12 UI images (5 runs) | 570 ± 66 ms | 561 ± 8 ms | 612 ± 68 ms |

How to read it:

- **Real differences:** susut is about 10 to 15% faster on JPEG batches (it processes files in
  parallel) and about 10 to 30% faster on WebP batches. Treat anything under roughly 10% as noise:
  in earlier sessions on the same machine a single JPEG was 4% *faster* in susut, here it is 5% slower.
- **Ties:** one JPEG, AVIF and PNG are the same within noise. The tools share the same encoders
  (mozjpeg, libwebp, rav1e, oxipng), so there is little to gain from orchestration there.
- **jpegoptim** is left out of the batch rows. On a single image it needs 37 ms, about four times
  faster, but only because `-m80` recompresses the existing DCT coefficients without decoding.
  The files come out 43% larger and baseline instead of progressive, and it cannot resize,
  convert or aim for a size.
- susut had the widest spread between runs in some sessions (610 to 1050 ms for the JPEG batch
  in one); I have not investigated why.

## Output size and quality

Same quality number for each tool. All numbers are totals over 12 files.

| Task | Input | susut | caesiumclt | rimage | Quality |
|---|---|---|---|---|---|
| JPEG q80 | 15,830,332 B | 4,276,893 B | 4,274,498 B | 4,276,893 B | PSNR 38.8 dB for all three |
| WebP q80 | 15,830,332 B | 6,193,348 B | 6,193,348 B | 6,193,348 B | PSNR 39.75 dB, same files |
| AVIF q80 | 2,617,920 B | 556,807 B | no AVIF | 556,807 B | PSNR 42.74 dB, same files |
| PNG, noisy | 17,395,442 B | 15,651,507 B (-10%) | 15,651,507 B | 15,651,507 B | pixel-identical |
| PNG, UI-like | 774,302 B | 665,145 B (-14%) | 665,145 B | 665,145 B | pixel-identical |
| JPEG, jpegoptim `-m80` | 15,830,332 B | | | | 6,117,395 B, PSNR 39.01 dB |

The tools produce the same bytes for WebP, AVIF and PNG, and almost the same for JPEG, which
confirms that they call the same encoders with the same settings. The only thing that differs
is time. PSNR is a rough sanity check, not a perceptual metric, and the same `-q` number does
not promise the same look across different encoders.

Lossless PNG gains depend entirely on the content: noisy images barely shrink, flat graphics
shrink more. Real screenshots usually do better than my synthetic UI images.

For `-s 150KB` on a 1.43 MB noisy JPEG, susut produced 153,160 bytes at quality 68 and
caesiumclt (`--max-size 153600`) produced 153,194 bytes. Both kept 3000x2000 pixels.

## Real photographs

To check the synthetic numbers I repeated the main tests on 11 real, public-domain NASA photos
(not stored in this repository; run [`run_real.sh`](../scripts/bench/run_real.sh) on any folder of
JPEGs). They are the originals of NASA image IDs `iss072e351732`, `iss072e351959`,
`iss072e352045`, `iss072e352235`, `iss072e352255`, `iss072e352275` (8256x5504 camera files),
`S06-46-617`, `STS047-20-015`, `sl3-114-1625`, `sl4-143-4706` and `sl4-143-4707`
(about 4000 px scans), 28.5 MB in total, from [images.nasa.gov](https://images.nasa.gov).
Same machine and settings, mean ± standard deviation:

| Task | susut | caesiumclt | rimage | Output size (susut / caesiumclt / rimage) |
|---|---|---|---|---|
| JPEG q80, full resolution (6 runs) | **3.21 ± 0.15 s** | 3.31 ± 0.11 s | 3.52 ± 0.07 s | 16.00 / 16.11 / 16.08 MB |
| JPEG q80, long edge 2000 px (6 runs) | 1.46 ± 0.03 s | 1.59 ± 0.03 s | **0.85 ± 0.01 s** | 2.55 / 2.78 / 2.62 MB |
| WebP q80, full resolution (3 runs) | **3.58 ± 0.08 s** | 5.91 ± 0.12 s | 4.85 ± 0.03 s | 11.46 MB, identical for all |
| AVIF q80, long edge 1600 px (3 runs) | 4.34 ± 0.08 s | no AVIF | 4.54 ± 0.04 s | 1.217 / n/a / 1.218 MB |

- Compression-only work behaves like the synthetic set: susut is level or ahead on JPEG and AVIF
  and ahead on WebP.
- **Resizing is susut's weak spot.** With a resize step (45 MP photos down to 2000 px) rimage is
  about 1.7 times faster, most likely because it uses a SIMD resizer while susut calls
  `resize_exact` of the `image` crate. Speeding that up is on the to-do list; I have not
  compared the visual quality of the three resize filters, so the size differences in that
  row say nothing about quality.
- **Skip-if-bigger in action:** a twelfth photo (NASA `GSFC_20171208_Archive_e000746`,
  1920x1080, 178,192 bytes, already well compressed) grew to about 182 KB when re-encoded at q80.
  susut left it alone and reported "skipped"; caesiumclt wrote the bigger file (+2.3%).
  That file is not part of the table above.

## Binary size after build

| Binary | Size | gzip | Notes |
|---|---|---|---|
| susut, macOS arm64 | 3.93 MB | 1.84 MB | release profile: LTO, `strip`, `opt-level 3` |
| susut, Linux aarch64 musl | 4.00 MB | 1.97 MB | static, no runtime dependencies |
| susut, Linux aarch64 glibc | 4.07 MB | 1.92 MB | needs glibc, libgcc_s, libm |
| caesiumclt 1.5.0, macOS arm64 | 6.26 MB | 2.46 MB | Homebrew build |
| rimage 0.14.0, macOS arm64 | 9.00 MB | 4.35 MB | built here with default features (more codecs) |
| jpegoptim 1.5.6, macOS arm64 | 76 KB | | dynamic, JPEG only |

These are not like-for-like: the tools have different feature sets (rimage includes JPEG XL and
more, caesiumclt includes GIF and TIFF) and were built with different settings. A cold
`cargo build --release` of susut takes about 35 to 45 seconds on this machine.

Peak memory for the JPEG batch (hyperfine, first session): susut 582 MiB, rimage 582 MiB,
caesiumclt 451 MiB, jpegoptim 44 MiB. susut decodes several 6 MP images in parallel, so
memory grows with the number of cores times the image size.

## musl or glibc?

Release binaries for Linux come in static musl and glibc variants. musl's allocator has a
reputation for being slow with many threads, so I timed both on the same JPEG batch in a
native arm64 Linux container (8 CPUs): glibc 1368 to 1473 ms, musl 1416 to 1478 ms.
No meaningful difference. x86_64 was not measured.

## Limits of these numbers

- One machine, one OS. The main tables use synthetic images; the real-photo section has only 11 images. Quality settings differ between encoders, so equal
  `-q` is not equal visual quality.
- Hyperfine run counts are small for AVIF (3) and PNG (5) because they are slow.
- If you get different results on real photos, please open an issue with your numbers.
